# 공지·강의자료 상세 조회 절감

## 수집 정책

- Toolbox의 공지·강의자료는 30분마다 전체 목록·페이지 수를 검증한다. 새 글, 목록 제목이 바뀐 글, 마지막 상세 확인에서 24시간이 지난 글만 상세 페이지를 연다.
- 조회수, 목록 순서, 페이지 번호는 변경 신호에서 제외한다. 원문 HTML과 첨부 접근 참조를 새 캐시에 저장하지 않는다.
- 저장된 실제 목록 응답에서 신뢰할 수 있는 본문 수정 시각을 확인하지 못했다. 조회수 증가 없는 상세 API도 확인되지 않았다. URL이나 요청 방식을 추측하지 않는다.
- 본문·링크·이미지·첨부 이름/개수 변경은 상세 재확인 시 기존 비교기로 감지한다. 제목 변화가 없으면 정상 수집 기준 약 24시간+다음 실행 대기까지 지연될 수 있으며, 사이에 수정됐다가 원복된 내용은 놓칠 수 있다. 장애 중에는 지연이 더 길어진다.
- 첫 적용 또는 확인 기록 유실 때는 한 번 전체 상세를 읽는다. 이후 변경 없는 글은 통상 하루 한 번만 읽는다. 조회수 증가를 완전히 없애는 정책은 아니다.
- 과제·시험·온라인 강의 수집은 그대로다. 별도 Discord Notifier 프로젝트와 서버 작업은 수정하지 않는다. 그 수집기가 실행 중이면 원본 조회수는 별도로 증가할 수 있다.

## 저장·실패 처리

`workers/lms/boards.py`가 검토된 Notifier의 탐색·파서·재시도를 재사용한다. 게시판 이동 부분은 기존 검증된 collector에서 옮겼으며 원본 DOM/URL 변경 시 함께 검토해야 한다.

보호된 private 디렉터리의 `board-checks.json`에는 게시물 식별자, 제목 지문, `detailCheckedAt`, 게시판별 목록 확인 시각만 기록한다. 공개 snapshot에는 추가하지 않는다. 원문·쿠키·첨부 참조는 기록하지 않는다.

전체 목록 검증과 상세 관측은 구분한다. `completeness_verified`는 전체 목록을 순회했다는 뜻이다. 결과 items/SQLite snapshots에는 이번 실행에서 실제 상세를 읽은 글만 들어간다. 건너뛴 글은 accepted_items의 이전 기준을 유지하며 삭제하거나 최신 관측으로 재저장하지 않는다. 첫 기준 생성 시에는 캐시만으로 건너뛰지 않는다. 확인 시각은 DB 커밋 이후에만 저장한다.

같은 실행의 과목 재시도에서는 성공한 상세 응답을 메모리에서 재사용한다. 실패한 과목은 확인 시각을 전진시키지 않는다. 프로세스 중단·DB 커밋 이후 파일 저장 실패 때는 다음 실행에서 중복 조회가 발생할 수 있다. UI의 마지막 성공은 수집 주기 성공 시각이며 모든 본문을 그때 읽었다는 뜻이 아니다.

검증은 합성 게시판·임시 SQLite를 사용한다. 변경 없는 글 상세 요청 0회, 24시간 재확인, 제목 변경, 과목 재시도 재사용, DB 기준 유실, 오래된 본문의 관측 시각 보존, 기존 본문 변경 이벤트를 검사한다. 실제 LMS·Discord에 검증 요청을 보내지 않는다.

Windows 전달 시 CHI-TOOLBOX-LMS 실행 상태를 확인하고 실행 중인 주기가 끝난 뒤 해당 작업만 잠시 비활성화한다. 기존 worker 파일을 별도 백업하고 `workers/lms/worker.py`, `projector.py`, `boards.py` 세 파일을 전용 worker 폴더에 전달한다. 별도 Notifier source와 private/public 데이터는 보존한다. 서버 Python으로 오프라인 테스트 후 기존 작업 활성 상태를 복원한다. 검증 목적으로 실제 수집을 강제 실행하지 않는다. 웹 앱 빌드·재시작은 필요 없다.

복구는 작업을 중지한 상태에서 이전 worker 파일을 복원한다. 새 확인 파일은 기존 수집기가 사용하지 않으므로 삭제할 필요가 없다. GitHub push는 수행하지 않는다.
