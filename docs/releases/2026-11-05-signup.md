# 회원가입 화면 · 2026-11-05

## 적용 범위

- `/dev/login` 안에서 회원가입으로 전환한다. PC는 간편 로그인 왼쪽, 이메일·비밀번호 가입 오른쪽이며 모바일은 세로 배치다.
- 로그인·가입 모드 모두 비밀번호 표시/숨김을 제공한다. 모드 전환 시 비밀번호를 비우고 다시 숨긴다. ‘이메일 로그인’ 문구는 유지한다.
- `POST /api/auth/signup`은 `{ ok: true, signedIn: boolean }`을 반환한다. 세션이 있으면 새 폼이 내부 `returnTo` 또는 `/dev/dashboard`로 이동한다. 세션이 없으면 가입 요청 처리 안내와 로그인 복귀를 제공한다. 응답에 인증 토큰을 포함하지 않는다.
- 양쪽 화면의 Google 버튼은 기존 `/api/auth/google?screen=dev&next=...`를 사용한다. 로그인과 최초 가입은 Supabase OAuth 정책이 처리한다. 별도 계정 조회·비밀번호 입력을 요구하지 않는다.
- 기존 `/login` 폼, 운영 도메인·Supabase 설정·데이터·LMS 수집 작업은 변경하지 않는다. 새 Google 제공자 추가나 DB migration은 없다.

## 검증

`npm.cmd run check`, `npm.cmd run build:test`, `npm.cmd run test:smoke`, `$env:TEST_BROWSER='msedge'; node scripts/run-browser-tests.mjs dev-login`을 통과했다. 단위 테스트는 18개다.

브라우저에서는 1440·390·320px 배치, 비밀번호 표시/숨김·초기화, 입력 검증, 오류 후 재시도, 가입 응답의 세션 유무, 로그인·가입 양쪽 Google 취소 복귀를 검사했다. 가입 응답은 mock이며 운영 계정을 만들지 않았다. 로컬 `preview:toolbox`는 dummy 인증을 사용하는 화면 확인용이다.

## 배포와 복구

운영 절차는 [Windows 배포](../../deploy/windows/README.md)를 따른다. 로컬 커밋을 Git bundle로 `chi-server`에 전달하고 서버의 깨끗한 소스를 fast-forward한 뒤 `deploy.ps1`로 운영 환경에서 다시 빌드한다. 로컬 dummy 빌드는 배포하지 않는다.

배포 전 운영 커밋은 `990ae73`, active 릴리스는 `20261104-221603-463-990ae73c2cc1`임을 SSH로 확인했다. 새 릴리스와 배포 후 검증 결과는 배포 완료 후 아래에 기록한다. 문제 발생 시 `deploy/windows/rollback.ps1`로 previous.txt의 앱 릴리스를 복원한다.

## 추가 확인

- 이메일 인증 비활성화는 사용자 설명이며 운영 설정을 변경하지 않았다.
- 실제 이메일 신규 가입과 Google 최초 가입·기존 계정 연결은 사용자 계정으로 별도 확인해야 한다. 자동 테스트·health 성공만으로 이를 완료로 간주하지 않는다.
- 이메일 인증을 나중에 활성화하면 확인 메일 안내와 콜백 목적지를 별도로 재설계·검증한다.
- 설정 화면의 항목·저장 범위가 다음 설계 대상이다.
